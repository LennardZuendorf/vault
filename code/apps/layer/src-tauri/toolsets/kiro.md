The spec is Kiro-style: requirements, then design, then tasks, in `{spec_dir}`.

- `requirements.md` (or `bugfix.md` for a bug): Goal, Requirements, Out of scope, Open questions. Each requirement is a list item with its id first, then the repositories that meet it in square brackets, then the requirement: `- R-3 [api, web]: WHEN a condition THE SYSTEM SHALL a behaviour.` With one repository, or one that every repository meets, leave the brackets out. A bug's `bugfix.md` has Current behaviour, Expected behaviour (`- R-1: ...`) and Unchanged behaviour (WHEN ... THE SYSTEM SHALL CONTINUE TO ...), numbered on from the last. Open questions are `- Q-1: ...`, `Q-2`, ..., with the answers they might take as an indented list under each; the user's answer is an `Answer:` line under the question.
- `design.md`: Approach; Contracts, each with its id first (`- C-1: ...`), saying what passes between repositories and which one provides it and which use it; then one `## <repo>` section per repository.
- `tasks.md`: steps, each `- [ ] 3. Call the refund endpoint (R-3, C-1; after api 2)`, numbered from 1 in order (within its repository when the file is grouped under `## <repo>` headings), naming the requirements and contracts it serves, then, after a `;`, the other repository's step it waits for (`after api 2` is step 2 of `api`).

Work in that order. Settle the requirements before the design, and the design before the tasks. Write each file in `{spec_dir}`; never inside a repository's worktree.
