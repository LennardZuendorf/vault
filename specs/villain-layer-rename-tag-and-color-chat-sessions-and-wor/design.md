# Design

Updated: 2026-11-27

## Approach

Add a profile-local presentation layer over existing chat and task identities. Use one editor in the existing row menus, one reusable text-tag catalog in Settings, and a tag grouping in Work. Expose the same field-level edits through three MCP tools. Preserve original titles and lifecycle behavior. No new dependency or server schema is needed.

- **Use local overrides (proposed).** This gives both item types the same controls and preserves automatic chat titles, PR title defaults, ticket links, and original names. Backend-owned local metadata survives relaunch and can report a failed save.
- **Change the existing titles in place (not proposed).** A task name also feeds PR defaults and context; a chat's CLI repeatedly supplies its title. Overwriting those names would either change other behavior or be undone by the next automatic title.
- **Store the details beside pins in webview storage (not proposed).** Pins are a useful precedent for the room key, but the existing storage wrapper silently ignores write failures. A separate webview store would also have to track the native task and chat lifecycles.
- **Derive tags from current assignments (not proposed).** This makes unused tags disappear and cannot represent tags added from Settings before they are assigned. A small catalog in the same profile file preserves both cases.

## Contracts

All components are in `vault`; nothing passes between repositories.

- C-1: The Layer Rust backend provides `ItemDetails` to the desktop frontend and mock: `{ display_name: string | null, tags: string[], color: "data-1" | "data-2" | "data-3" | "data-4" | "data-5" | "data-6" | null }`. Missing details mean no override, no tags, no color. Rust is authoritative for normalization and validation.
- C-2: The desktop frontend sends the edited fields of `ItemDetails` through `src/lib/api.ts` to `set_task_details` (`{ taskId, patch }`) or `set_chat_details` (`{ room, patch }`). Omitted fields remain unchanged, `null` clears the name or color, and `[]` clears assigned tags. Rust validates and persists one change for an eligible item and returns canonical details or an error. Desktop task, open-pane, and waiting-pane list responses add optional `details`. The mock implements the same contract.
- C-3: `list_tags` returns the profile's canonical tag names as `string[]`. `add_tag` (`{ tag }`) validates and returns the canonical spelling, reusing a case-insensitive match. Saving a new tag assignment adds a missing catalog entry in the same transaction. A successful changed write emits `item-details:changed`, for the desktop to refresh the affected list and, when needed, the catalog. The event identifies the affected kind (`task`, `chat`, or `catalog`) and whether the catalog changed.
- C-4: The profile's existing authenticated MCP server provides `task_rename({ task_id?, name })`, `task_set_tag({ task_id?, tag, assigned })`, and `task_set_color({ task_id?, color })`. A `name` or `color` of `null` clears that value. `assigned` is a required boolean; removing an unassigned tag does nothing. An explicit `task_id` refers only to an existing Work task. Without it, Layer resolves the current pane's eligible Work task or standalone Chat room. An absent or ineligible caller and an unknown explicit task are errors. Each tool returns the canonical details and does not replace unspecified fields.

## vault

Paths below are relative to `code/apps/layer/`.

### Local state and commands

- Keep two default-empty maps in `AppConfig`: task details by `Task.id`, and chat details by existing room path, never pane ID or ACP session ID. Keep a default-empty catalog of text tags beside them. Check chat eligibility against the saved Chat record; exclude Henchman, routine and task-owned panes. Treat the room path as an opaque lookup key, not as a path to open.
- Project task details only in the desktop `list_tasks` command, not in `Task` or the `TaskView` returned by `list_tasks_inner`: MCP serializes both those types. Project chat details only in the desktop `list_panes` and `waiting_panes` responses. Do not replace `Task.name`, `sub_task.title`, launch title, CLI topic, or transcript title. PR and diff title defaults, generated context, and run history keep their source names.
- Use `#[serde(default)]` for the new persisted fields. Keep details out of `config/shared.rs`, workspace data, and existing phone, agent and Slack payloads. Remove empty item entries, but retain the catalog. Clean up a task's entry when its task record is removed, including when removing its last repository drops it. Clean up chat details on intentional ordinary-chat close or explicit waiting-chat forget. Retain them on temporary stop, internal restart, restore, or close of a chat still linked to a Slack thread. Do not remove saved transcripts.
- Use the profile's config disk lock for validation and the write. `ConfigStore::update` currently changes memory before it persists. For this metadata path, use a narrow persist-before-publish operation following the locking pattern of `ConfigStore::mirror`; do not change unrelated callers' write behavior. Run disk work through `commands::blocking`. Check that the item still exists as part of the protected mutation.
- Normalize in Rust before writing. Reject raw control characters and Unicode line/paragraph separators before trimming. Count limits in Unicode scalar values and deduplicate nonempty tags case-insensitively, keeping assignment order. The first saved catalog spelling wins. Add one nonempty tag in Settings or MCP; reject a blank tag there. An invalid or failed assignment must not leave a new catalog entry.
- Register the Tauri commands in `src-tauri/src/lib.rs` and wrap them in `src/lib/api.ts`. Mirror payloads in `src/lib/types.ts`. Route MCP in a focused tool module using the same backend edit operations, profile authentication, and blocking helper. The existing pane header identifies a target for routing, not a credential. Resolve and merge the three MCP edits under the same config write lock as desktop edits, so concurrent edits to different fields are not lost.
- After a successful change, listen once in `Watchers.tsx` and refresh the affected task or pane/waiting lists and the catalog when needed. Compare details in `samePane` so unchanged rows keep their identities. Serialize or discard stale refresh responses; a response requested before a save must not replace the new display state. Add no poll.

### Desktop presentation

- Add **Edit details…** to the existing `ContextMenu` entry points in `ChatView.tsx`, `WaitingPanes.tsx`, and `sidebar/Sidebar.tsx`. Use one `Modal` with separate fields for display name, tags and color. Show the automatic name as a placeholder, catalog choices and removable text chips for tags, and named palette choices (Lavender, Cyan, Rose, Blue, Amber, Mint, and No color). Allow typing a new tag. Save commits the edited fields as a unit. Cancel or Escape before submit discards the draft. While saving, prevent duplicate submits; use `useFailure` and `ErrorMessage` for inline failures. Do not show a success toast.
- Add a local **Tags** tab in `Settings.tsx` and a `TagsSettings.tsx` panel. List canonical text names and provide a labeled field with an **Add tag** action. Use the same catalog in both editors. A tag has no color, icon, or separate editable metadata; the item color is independent.
- For chats, use the override only for desktop display. Apply it in `ChatList.tsx`, `WaitingPanes.tsx`, `ChatLink.tsx`, `AgentsView.tsx`, and the shared `paneName` path in `src/lib/derive.ts` used by agent pickers. Also use it where Chat identifies the room in its own close dialog. Preserve each surface's fallback order, including the Slack label when applicable. Never replace the title passed to an agent.
- For Work, use the override first in `sidebar/TaskRow.tsx`, `sidebar/EpicRow.tsx`, and the selected heading in `App.tsx` or `EpicView.tsx`. Preserve each surface's fallback, including the spec title on a filed subtask row. Extend `src/lib/task-search.ts` to include the alias and tags without removing source text; keep `EpicsSection.tsx` matching rules.
- Add `tag` to Work's persisted grouping choices in `sidebar/Sidebar.tsx`. For that mode only, flatten the existing filtered task and epic sections into unique stored task IDs before applying the usual stage order. Use a pure `byTag` helper in `src/lib/grouping.ts` to put each task under each of its tags. Sort named headings by normalized tag name and keep stage order within each heading. Give the final **No tag** bucket a reserved key distinct from any user tag. The existing epic tree remains unchanged in the other modes.
- Use neutral `ui-chip` tags and a separate, named color indicator from `--data-1` through `--data-6`. Do not use the activity dot, status tokens, or a full-row tint for the color. Keep branch and thread links in place. Check keyboard focus, accessible labels, narrow rows, and day/night presentation. This follows the studio's **Show less**, **Even colour**, and **The accent stays out of the neutrals** principles.

### Verification seams

- Rust tests use a temporary profile config to prove old data loads, edits survive reload, failures do not publish changes, and cleanup follows the correct lifecycle. Test catalog reuse and profile isolation, and same-room/new-pane-ID restore and Slack retention separately from ordinary close and explicit forget. Exercise MCP dispatch for a supplied Work ID, inferred Work task and inferred Chat room, invalid targeting, removal and clears, field isolation, and post-save notification.
- Bun tests cover name fallback, per-item details after refresh, search across existing fields and labels, and tag grouping with multiple tags, nested tasks, and untagged items. Mock fixtures and command responses exercise open, pinned, waiting, and Slack chats and linked, ticketless, and nested Work tasks. Update Layer's `docs/features.md` before code and document IPC and the new event in `docs/architecture.md`.
